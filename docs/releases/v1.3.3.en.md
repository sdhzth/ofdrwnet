# NetOfd v1.3.3

## Minor release: `defaults` namespace compliance, page-level resource support, standard font naming

This **minor release** closes three OFD conformance gaps: the `defaults` namespace declaration on
root nodes, bidirectional support for page-level resources (`PageRes.xml`), and standard naming of
font resources.

### 📐 Conformance: `defaults` namespace declaration

**Standard basis**: GB/T 33190-2016 §7.1 and GB/T 48666-2026 §6.2 require that
"the root node of each XML file inside the container shall declare `defaults:ofd`" — i.e. besides
`xmlns:ofd`, the root node must also declare `xmlns:defaults="http://www.ofdspec.org/2016"`, so
that the same namespace carries both the `ofd` and the `defaults` prefix and implementations
parsing by the `defaults:` prefix keep working.

**New API** (`NetOfd.Core.OFDElement`):

| Method | Purpose |
|---|---|
| `InjectDefaultsDeclaration(string xml, string ns)` | Adds the declaration to the root start tag at the XML **text** level (idempotent) |
| `InjectDefaultsDeclarationBytes(byte[] content, string ns)` | Same, returning bytes |
| `InjectDefaultsDeclarationToMap(Dictionary<string, byte[]> map, string ns)` | Bulk-processes every OFD XML in a mapped container; returns the number of entries touched |
| `NormalizeOfdXmlBytes(byte[] content, string ns)` | Normalization: inject the declaration + restore element prefixes |
| `RestoreOfdPrefix(string xml)` / `RestoreOfdPrefixBytes(byte[])` | Restores elements whose prefix was rewritten to `defaults:` back to `ofd:` |

**⚠️ Deprecated**: `EnsureDefaultsNamespace(XElement)` / `EnsureDefaultsNamespaceBytes(XDocument)`.

> **Pitfall (important)**: LINQ-to-XML cannot express "two prefixes for the same namespace".
> Measured on .NET 10: after appending `new XAttribute(XNamespace.Xmlns + "defaults", uri)` to any
> root element, serialization rewrites the **element prefix** from `ofd:` to `defaults:`, and
> attribute names follow suit (`defaults:Version`) — for all three input shapes tested. This
> clearly violates GB/T 33190-2016 §7.1 ("element nodes shall use the namespace identifier, `ofd`").
> Injecting as a string first and re-parsing via `XElement.Parse` does not help either: the prefix
> is rewritten again on serialization. Hence **no path that serializes through LINQ-to-XML can
> produce a correct dual-prefix document** — the only viable route is to insert the attribute
> declaration directly into the **already serialized text**. This finding is locked in as a
> regression test:
> `DefaultsNamespaceTest.LinqToXml_CannotExpressDualPrefix_ThisIsWhyTextInjectionIsRequired`.

**Wiring points**:

- `NetOfd.Layout.Edit.ZipMapIO` — the **single exit** for XML produced by the mapping-style
  editor; the injection is consolidated there so that documents written by the editor match the
  container-layer output;
- `NetOfd.Emr.OfdHDocumentGenerator` — injection happens **before signing** (signature values and
  integrity signature values are digests over file bytes, so changing bytes after signing
  invalidates the signature). `OFD.xml` is the exception: the signing step rewrites it through
  LINQ-to-XML (to append the `Signatures` entry), so the injection for `OFD.xml` is performed by
  `OfdSigner` after that rewrite and before the digest is computed.

### 🗂️ New: bidirectional support for page-level resources (`PageRes.xml`)

**Standard basis**: GB/T 48666-2026 §7.2 a — "fonts, drawing parameters and resources shared by
multiple pages that are used by the document page content **shall** be registered in the document
resource list (`DocumentRes.xml`); resources used within a single page only **are generally**
registered in the page resource list (`Page_N/PageRes.xml`)." The first half is mandatory, the
second half is recommended.

**Reading side (`NetOfd.Reader.ResourceManage`)**: previously only two kinds were loaded — public
resources (`Doc_N/PublicRes.xml`) and document resources (`Doc_N/DocumentRes.xml`) — matching the
Java source comment "page resources, ignored for now". The third kind is now supported: page
resources at `Doc_N/Pages/Page_M/PageRes.xml` (registered by each page's `Content.xml`), all three
feeding the same resource pool. Path resolution semantics (the `BaseLoc` rules) stay consistent
with Java's `abs()` and ofdgo's `resolveResourcePath`.

**Writing side (`NetOfd.Layout.ResManager`)**: new `MediaPlacement` placement policy enum.

| Value | Behaviour |
|---|---|
| `Auto` (default) | Resources referenced by a single page sink into `Page_N/PageRes.xml` + `Page_N/Res/`; resources shared by several pages, or whose reference scope cannot be determined, are registered at document level in `DocumentRes.xml` + `Doc_0/Res/` |
| `DocumentOnly` | Everything is registered at document level (the Java ofdrw baseline — `ResManager#addMultiMedia` always calls `docRes()`). Use it when byte-identical output with older artifacts is required, or when downstream readers do not support page-level resources |

Accompanied by `ResManager.Placement`, `ResManager.CurrentPageLoc` and
`ResManager.PlaceMediaResources(DocDir)` — the on-disk location of a media resource is decided
later, once its actual reference scope is known.

**Structure layer (`NetOfd.Core.PageObject`)**: new `AddPageRes(STLoc loc)` declares a page
resource file.

> **Schema ordering matters**: per GB/T 33190-2016 table 13 (`CT_Page`), the child element order is
> `Area, Template*, PageRes*, Content?` — meaning `PageRes` **must come before `Content`**. A
> plain `Add` would place it after `Content` and break the Schema order (both ofdgo and Java ofdrw
> parse in that order). The method is idempotent: declaring the same loc twice writes it once.

### 🏷️ Improvement: standard font resource naming (`Font_M.ttf`)

When generating OFD-H documents, `NetOfd.Emr.OfdHDocumentGenerator` now names font resources per
GB/T 48666-2026 table 1 as `Font_M.ttf` (M = the font resource sequence number, numbered
consecutively per type). The number is the highest existing `Font_*.ttf` sequence plus one, so it
never collides with font resources already in the package. The previous semantic name
`Font_FangSong.ttf` is gone.
