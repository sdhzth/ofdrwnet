# NetOfd v1.3.3

## 小版本：`defaults` 命名空间合规、页面级资源支持、字型资源规范命名

本次为**小版本（minor）**，聚焦 OFD 规范合规性的三项补齐：根节点 `defaults` 命名空间声明、
页面级资源（`PageRes.xml`）读写双向支持、字型资源按标准命名。

### 📐 合规：`defaults` 命名空间声明补齐

**规范依据**：GB/T 33190-2016 §7.1 与 GB/T 48666-2026 §6.2 要求
「容器内各 XML 文件的根节点中应声明 `defaults:ofd`」——即根节点除 `xmlns:ofd` 外，
还须额外声明 `xmlns:defaults="http://www.ofdspec.org/2016"`，使同一命名空间同时具备
`ofd` 与 `defaults` 两个前缀标识，以兼容按 `defaults:` 前缀解析的实现。

**新增 API**（`NetOfd.Core.OFDElement`）：

| 方法 | 作用 |
|---|---|
| `InjectDefaultsDeclaration(string xml, string ns)` | 在 XML **文本**层面为根开始标签补齐声明（幂等） |
| `InjectDefaultsDeclarationBytes(byte[] content, string ns)` | 同上，直接返回字节 |
| `InjectDefaultsDeclarationToMap(Dictionary<string, byte[]> map, string ns)` | 批量处理映射式容器内的全部 OFD XML，返回处理条数 |
| `NormalizeOfdXmlBytes(byte[] content, string ns)` | 归一化：注入声明 + 还原元素前缀 |
| `RestoreOfdPrefix(string xml)` / `RestoreOfdPrefixBytes(byte[])` | 把被改写成 `defaults:` 前缀的元素还原回 `ofd:` |

**⚠️ 已废弃**：`EnsureDefaultsNamespace(XElement)` / `EnsureDefaultsNamespaceBytes(XDocument)`。

> **踩坑记录（重要，务必了解）**：LINQ-to-XML 无法表达「同一命名空间的两个前缀」。
> 实测（.NET 10）：对任何根元素追加 `new XAttribute(XNamespace.Xmlns + "defaults", uri)` 后再序列化，
> LINQ 会把**元素前缀**由 `ofd:` 改写为 `defaults:`，属性名亦随之变成 `defaults:Version`
> 形式（S1/S2/S3 三种输入均如此），严重违反 GB/T 33190-2016 §7.1
> 「元素节点应使用命名空间标识（标识为 ofd）」。即便先做字符串注入再 `XElement.Parse` 回解析，
> 序列化时同样被改写为 `defaults:`——故**任何经 LINQ-to-XML 序列化的路径都无法正确产出双前缀文档**，
> 唯一可行路径是在**已序列化的文本**上直接插入属性声明。该结论已由
> `DefaultsNamespaceTest.LinqToXml_CannotExpressDualPrefix_ThisIsWhyTextInjectionIsRequired`
> 固化为回归用例。

**接入点**：

- `NetOfd.Layout.Edit.ZipMapIO` —— 映射式编辑器产出 XML 的**唯一出口**，在此统一收口，
  保证编辑器写出的 OFD 与容器层产物一致；
- `NetOfd.Emr.OfdHDocumentGenerator` —— 在**签名之前**完成注入（签名值与完整性签名值均是对
  文件字节的杂凑，若在签名之后再改字节，签名将无法验证）。`OFD.xml` 例外：签名步骤会用
  LINQ-to-XML 重写它（追加 `Signatures` 入口），故 `OFD.xml` 的注入改由 `OfdSigner` 在重写之后、
  计算杂凑之前完成。

### 🗂️ 新增：页面级资源（`PageRes.xml`）读写双向支持

**规范依据**：GB/T 48666-2026 §7.2 a —— 「被文档页面内容使用的字型、绘制参数和在多个页面中
共同使用的资源**应**在文档资源列表（DocumentRes.xml）文件中注册，仅在一个页面内使用的资源
**一般**在页面资源列表（Page_N/PageRes.xml）文件中注册。」前半句为强制条款，后半句为推荐性条款。

**读取侧（`NetOfd.Reader.ResourceManage`）**：此前只加载公共资源（`Doc_N/PublicRes.xml`）
与文档资源（`Doc_N/DocumentRes.xml`）两类（Java 版源码注释「页面资源，暂时忽略」）。
本次补齐第三类 —— 页面资源 `Doc_N/Pages/Page_M/PageRes.xml`（由各页 `Content.xml` 登记），
三者汇入同一资源池。路径解析语义（`BaseLoc` 规则）与 Java 的 `abs()` 及 ofdgo 的
`resolveResourcePath` 保持一致。

**生成侧（`NetOfd.Layout.ResManager`）**：新增 `MediaPlacement` 落位策略枚举。

| 取值 | 行为 |
|---|---|
| `Auto`（默认） | 仅被单个页面引用的资源下沉到 `Page_N/PageRes.xml` + `Page_N/Res/`；多页共用、或引用范围无法判定的资源登记到文档级 `DocumentRes.xml` + `Doc_0/Res/` |
| `DocumentOnly` | 全部登记到文档级（Java ofdrw 生成侧基线行为，`ResManager#addMultiMedia` 一律 `docRes()`）。需要与旧产物逐字节一致、或下游阅读器不支持页级资源时使用 |

配套新增 `ResManager.Placement`、`ResManager.CurrentPageLoc` 与
`ResManager.PlaceMediaResources(DocDir)` —— 媒体资源的落盘位置延后到按实际引用范围决定。

**结构层（`NetOfd.Core.PageObject`）**：新增 `AddPageRes(STLoc loc)` 声明页面资源文件。

> **注意 Schema 顺序**：GB/T 33190-2016 表 13（`CT_Page`）的子元素顺序为
> `Area, Template*, PageRes*, Content?`，即 `PageRes` **必须排在 `Content` 之前**；
> 直接 `Add` 到末尾会插在 `Content` 之后而违反 Schema 顺序（ofdgo / Java ofdrw 均按此顺序解析）。
> 该方法幂等：同一 loc 重复声明只写一次。

### 🏷️ 改进：字型资源按标准命名（`Font_M.ttf`）

`NetOfd.Emr.OfdHDocumentGenerator` 生成 OFD-H 文档时，字型资源改按 GB/T 48666-2026 表 1
规范命名 `Font_M.ttf`（M 为字型资源序号，按类型连续编号），序号取包内已存在的 `Font_*.ttf`
最大者 +1，避免与既有字型资源重名。此前使用语义化名称 `Font_FangSong.ttf`。
